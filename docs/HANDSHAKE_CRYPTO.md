# OGTP/1 Hybrid Key Exchange and Handshake Protection

Status: **draft 0.2 implementation contract; audited provider required**.

This document specifies `src/handshake_crypto.rs`: the provider-neutral
X25519/ML-KEM-768 orchestration, HKDF-SHA-384 schedule, Finished generation,
and AEAD protection for `RESPONSE` and `FINISH` identity blocks. It fixes
operation order, failure behavior, memory ownership, and type-state gates. It
does not claim that any concrete post-quantum implementation has been audited.

## Provider boundary

`HandshakeCryptoProvider` supplies only standardized operations:

- ephemeral X25519 key generation and agreement;
- ML-KEM-768 key generation, encapsulation, and decapsulation;
- SHA-384, HMAC-SHA-384, HKDF-Extract, and HKDF-Expand;
- AES-256-GCM or ChaCha20-Poly1305 handshake AEAD.

All public-key, ciphertext, shared-secret, digest, key, IV, tag, and plaintext
lengths are present in Rust array types. The provider owns secure randomness,
opaque private-key types, canonical ML-KEM input validation, ML-KEM implicit
rejection, constant-time implementation, secret-key destruction, hardware
handles, and backend error hygiene.

An invalid AEAD tag is distinct from provider failure. ML-KEM decapsulation
must follow FIPS 203 implicit rejection: an attacker-controlled ciphertext does
not become a distinguishable decapsulation-validity error. Authentication of
the derived secret occurs when the fixed handshake AEAD is opened.

The default library contains no KEM, curve, HKDF, HMAC, or handshake-AEAD
implementation. Test providers reproduce the published HKDF vector and the
orchestration failure paths; they are not production providers.

## Initiator state

`generate_initiator_hybrid_state` asks the provider for one ephemeral X25519
pair and one ML-KEM-768 pair. `InitiatorHybridState` owns the two opaque private
handles and fixed public values:

```text
X25519 Public Key[32] | ML-KEM-768 Encapsulation Key[1184]
```

These values are copied into canonical `INIT`. The state is neither cloneable
nor externally constructible. Processing `RESPONSE` consumes it on success or
failure, so neither private key can be reused with another response.

Completion computes X25519 with the responder key and decapsulates the exact
1,088-byte ML-KEM ciphertext. The orchestration independently OR-reduces all 32
X25519 output bytes and rejects the all-zero result before HKDF.

## Responder state

`respond_to_initiator` generates a fresh responder X25519 pair, computes the
X25519 secret, encapsulates to the exact initiator ML-KEM key, and derives the
schedule before returning anything. Its result owns:

```text
Responder X25519 Public Key[32]
ML-KEM-768 Ciphertext[1088]
Directional Handshake Secrets
```

A failure in either hybrid branch or any KDF stage returns no installable
secret result. The responder's ephemeral X25519 private handle is dropped after
derivation.

## Hybrid and HKDF schedule

The two fixed shared secrets are immediately combined in the normative order:

```text
hybrid_shared_secret = ml_kem_shared_secret[32]
                    || x25519_shared_secret[32]
```

The 64-byte value is never returned by a public API. It is fed directly into
the schedule in `CRYPTO.md`. The implementation derives:

- initiator and responder handshake traffic secrets;
- role-specific Finished keys;
- role-specific 32-byte AEAD keys and 12-byte IVs;
- the deferred master secret.

Every label is generated by the canonical `encode_expand_label` codec. The
implemented schedule is tested byte-for-byte against
`test-vectors/kdf-sha384-v1.txt`, including both handshake directions and the
two application secrets.

Temporary shared secrets, extraction stages, traffic keys, and IVs use fixed
`SecretBytes` storage with redacted diagnostics and logical overwrite on drop.
No KEM or KDF path allocates based on network input. Compiler-proof physical
zeroization still belongs to the audited provider and platform integration.

## Finished values

`HandshakeSecrets::compute_finished` selects the key by sender role and asks
the provider for:

```text
HMAC-SHA-384(sender_finished_key, named_transcript_hash)
```

It returns the 48-byte MAC, never the handshake AEAD key. The Finished-key
accessor exists only because the separate authentication orchestration verifies
received Finished values through its provider boundary. Callers must use
`TH_r_finished` for the responder and `TH_i_finished` for the initiator.

## RESPONSE and FINISH AEAD

The API has separate role-specific entry points rather than a generic public
seal/open function:

- `seal_responder_identity_auth` / `open_responder_identity_auth` use `r_hs`
  material and `TH_pre_auth` AAD;
- `seal_initiator_identity_auth` / `open_initiator_identity_auth` use `i_hs`
  material and `TH_i_signature` AAD.

Both use:

```text
nonce = sender_handshake_iv XOR left_pad_96(message_id_u32)
```

Only the low four IV bytes are XORed. The canonical 5,405-byte `IdentityAuth`
plaintext is sealed to exactly 5,421 bytes. The logical ciphertext is cached
and fragmented after sealing; retransmission reuses its bytes and does not call
the AEAD provider again.

Each directional secret contains a one-way sealing reservation. The bit is set
before the provider call and is never rolled back after provider failure or
length mismatch. A caller therefore cannot accidentally reuse the same
key/nonce by retrying encryption. Failed sealing clears the complete output
region.

Opening copies the fixed ciphertext into one 5,421-byte candidate object. An
invalid tag, provider error, length mismatch, or plaintext codec error destroys
that candidate and returns no plaintext reference. On success the tag tail is
cleared and `OpenedIdentityAuth` exposes only the 5,405 authenticated bytes. Its
storage and `Debug` representation are cleared/redacted on drop.

AEAD success proves possession of the hybrid handshake secret but does not
authenticate the peer identity. The caller must next advance the transactional
transcript and pass its named snapshots plus the decoded plaintext to
`authenticate_peer_identity`.

## Application-secret gate

`derive_application_secrets` consumes all handshake traffic material. It does
not accept a caller-supplied raw hash alone. The caller must provide both:

- `InitiatorTranscriptMilestone`, proving the transcript reached `TH_full`;
- `AuthenticatedIdentity`, proving trust-anchor, Finished, Ed25519, and
  ML-DSA-65 verification succeeded.

Only then are `i_ap_0` and `r_ap_0` returned. This type-state gate prevents a
successful KEM, malformed full hash, or AEAD-only peer from installing
application traffic secrets through the public API.

## Fixed memory and logging

Large public values use exact arrays: 1,184 bytes for the initiator ML-KEM key
and 1,088 bytes for the responder ciphertext. Shared secrets are 32-byte fixed
buffers and the combined HKDF input is 64 bytes. The largest candidate buffer
is the 5,421-byte encrypted authentication value. Memory is independent of
fragment count, object size, path count, or attacker-declared lengths.

Key-exchange states, directional schedules, opened plaintext, application
secrets, and provider-owned private handles are redacted from `Debug`. Provider
error values must never contain private keys, shared secrets, HKDF stages,
traffic keys, IVs, plaintext, or complete transcript hashes.

## Required event-loop order

Responder:

1. authenticate the stateless cookie and obtain an admission lease;
2. reassemble and decode canonical `INIT`;
3. advance the transcript through the `RESPONSE` prefix and obtain
   `TH_pre_auth`;
4. run both hybrid branches and derive the schedule;
5. construct signatures and responder Finished;
6. seal responder `IdentityAuth` once, then cache/fragment `RESPONSE`;
7. reassemble/open `FINISH`, advance the transcript, and authenticate the
   initiator;
8. derive application secrets using the completed-transcript and authenticated-
   identity capabilities.

Initiator:

1. generate and retain one initiator hybrid state before encoding `INIT`;
2. reassemble/decode `RESPONSE` and obtain `TH_pre_auth` from its prefix;
3. consume the hybrid state to derive the same schedule;
4. open responder authentication, advance the transcript, and authenticate the
   responder;
5. construct and seal initiator authentication once, then cache/fragment
   `FINISH`;
6. complete the transcript and derive application secrets through both
   capability gates.

Any terminal error discards the handshake, admission lease, reassembly slot,
ephemeral provider handles, transcript state, and derived secret schedule.

## Validation and remaining work

Deterministic tests cover initiator/responder agreement, normative hybrid
ordering, all-zero X25519 rejection, published HKDF values, Finished equality,
role-separated AEAD, message-ID nonces, AAD/role/ciphertext tampering, one-way
seal reservation, provider failure and length faults, candidate plaintext
containment, application derivation, and diagnostic redaction.

Production work still includes:

- audited X25519 and ML-KEM-768 provider adapters with real known-answer and
  malformed-input tests;
- audited AES-256-GCM/ChaCha20-Poly1305, HKDF, HMAC, and secure-key storage;
- complete encrypted `RESPONSE` and `FINISH` interoperability vectors;
- stateful fuzzing across KEM failure, transcript rollback, AEAD failure, and
  capability installation;
- compiler/platform verified zeroization and opaque-handle destruction;
- batched-runtime CPU, stack, cache, and invalid-ciphertext measurements;
- formal verification of hybrid composition, authentication, downgrade
  resistance, and key separation.
